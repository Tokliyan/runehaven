### Fixed tonight (2) — both inside Plains scope, neither changes a pixel

**F1. `windAmpNow` could be NaN-poisoned from `localStorage`, and the whole
forge would go quietly blank.** `WIND_AMP` is an object literal, so
`WIND_AMP["__proto__"]`, `["constructor"]`, `["toString"]`, `["valueOf"]` and
`["hasOwnProperty"]` are **not** `undefined` — the "unknown stored value reads
as Full" fallback never fired for them. `loadSettings` accepts any persisted
**string** for this key (it checks `typeof` against the default, not the value),
so a save holding one of those five made `WIND.amp` an object or a function.
Truthy, so `windLean` returned NaN; `pbLeanFrame(NaN)` is NaN (neither `< -2`
nor `> 2`); every forge key then carried `"NaN"`, every bake drew nothing and
cached a 1x1 transparent sprite, and every weather particle took `x = NaN` and
was never recycled, because `NaN < lo || NaN > hi` is false. No grass, no trees,
no weather, no error, for the rest of the session — and the dead sprites are
cached, so it would survive a camera move. Verified over all 13 candidate
values. Now a `WIND_MODES` membership test, the same test `refreshSettingsUI`
already uses one line away; `off` / `low` / `full` still read 0 / 0.5 / 1
exactly, so nothing about the look changes.

**F2. The Plains 1.15x cost gate could not tell a working layer from an empty
one.** It compared `onBaked4 / offBaked4` and `onLive4 / offLive4` against 1.15
and nothing else. Make `pbDrawTree` return `false` for every tree and the world
loses its forged trees while the ratio goes to ~1.000 and the gate **passes**;
the still-frame gate beside it does not cover that either, because it is
satisfied by the tuft keys alone, and run6's bake gate calls `pbTreeSprite()`
directly rather than through the draw path. A 15th gate now requires the ON
measurement to show its work — tufts drawn on the last frame, and forged trees
and baked ground props over the run, against none with the switch off.

**F20. The wind band gate was flaky, and it failed tonight. Pinned, not
relaxed.** Not from a reviewer — the first run4 of the night found it: 2192
PASS and **1 FAIL**, `Living World S4 wind: a gust is ONE band crossing the
world in order`. It is not a regression, and I proved that before touching
anything. 1a pinned the world CLOCK for the whole S4 block precisely because
"an un-pinned wind gate measures a different wind on every run" — but the
wind's base direction is `hash2(worldSeed, 17, 9931) * 6.2832`, so it is the
SEED as much as the clock, and the seed was left unpinned. Earlier blocks in
`run4.js` leave the world on whatever seed they finished with.

The gate has two halves. The scale-free half — the profile one second later
matches the profile shifted downwind by `WIND_GUST_SPEED` at least four times
better than the unshifted one — **passed at every probe** (ratios 0.084, 0.038,
0.011 against a limit of 0.25), as did the crest spacing (11.0 tiles, r 0.998)
and the tree-stiffness check (0 of 400 wrong). The half that failed is an
ABSOLUTE cap of 0.03 on the residual, and that cap is calibrated against one
seed's envelope amplitude: the run measured 0.0447 against 0.5292 unmoved,
where seed 123456789 gives 0.0138 against 0.1824 — the same ratio, a bigger
wind.

Confirmed by solving for it rather than by assuming: reimplementing `windGust`
standalone and sweeping the base angle reproduces all six printed figures to
**2e-4** at an angle of **6.268 rad** (hash2 0.9976), which is no seed this
harness sets — while the four seeds it does set (1, 123456789, 424242,
987654321) all pass. So the band was crossing the world in order the whole
time, at a wind the gate had not been calibrated for.

Fixed by pinning the seed beside the clock, `S4_SEED = 123456789`, restored in
the block's own `finally` next to the clock restore. **No threshold was
touched** and no assertion was loosened; the figure is simply reproducible now.
Recorded here and in GAUNTLET_PROGRESS because it is a change to an existing
gate, which is the one kind of harness edit that has to be declared.

### Reported, not fixed — and why each one was left

Nothing below is fixed, for one of three reasons: it is **not Plains** (the
slice says fix Plains scope and report the rest), it would **change how Plains
looks** (the slice forbids that), or it is a **design question** the README does
not settle (NEXT_BUILD rule 3 says not to decide those). The reason is stated
for each.

**F3. `WIND.sx` is discontinuous at zero, so the whole field's lean flips sign
in a single frame.** *(Plains; would change the look; also a design question.)*
`WIND.sx = sx >= 0 ? 0.4 + 0.6*sx : -0.4 + 0.6*sx` — a deliberate ±0.4 dead zone
so a wind blowing "into" the screen still leans things, which also means it jumps
from +0.4 to −0.4 as the drifting direction crosses. Measured over two hours of
world clock at four seed phases: **4 to 12 sign flips**, a single-frame step in
the lean of up to **0.49**, and a jump of **two baked lean frames at once**
(+1 straight to −1, skipping 0). With `plains: true` that is every tuft and
every tree on screen snapping its lean direction together, several times an
hour. **This is the one thing I would want you to look at before flipping the
switch.** Fixing it means choosing what a wind blowing into the screen should do
— keep a floor but move continuously through it, or lose the floor — which is a
feel decision, and any version of it changes the GIFs above.

**F4. The weather no longer looks like `main` with every switch false.**
*(Not Plains; and the README asks for it.)* `pbAirWeatherDrift` is the one hook
in the module gated on `WIND.amp` alone and on no `PIXEL_BIOMES` switch, so
rain, snow and ash take a wind-driven sideways drift in the shipped
configuration. Measured: rain −25.1…+32.3 px/s on top of its own −40, snow
−16.3…+21.0 on top of +8, ash −15.9…+20.4 on top of +14, with a hard non-zero
floor of 5.2–8.3 px/s from the dead zone in F3. Ash and snow change direction
outright. This is **intended** — README pillar 1 says "leaves, petals, seeds and
rain slant the same way", and the Wind motion setting is a global feature, not a
per-biome one — but it does mean the module header's sentence *"Every biome
draws exactly as before Session 4 while its switch is false"* is true of biomes
and not of the weather layer. Wind motion: Off or Reduce motion makes it
bit-identical to `main` again. Three consequences worth knowing:
- F3's sign flip lands on the weather too: once every ~7 minutes the whole rain
  field's horizontal velocity snaps by up to 25.7 px/s in one frame, and ~10% of
  the 160 flecks fall outside the recycle window on that frame and are all
  re-seeded at the top together.
- The spawn window is sided by `sign(wdr)` rather than `sign(P.vx + wdr)`. Since
  snow and ash have a positive base `vx`, a leftward gust widens the window on
  the *wrong* side and those particles fall off the bottom unseen: simulated
  over 400 s, mean on-screen ash drops from 146.6 to **119.6 (82%)** and snow to
  128.8 (88%). A thinner ashfall than `main` has.
- The window itself is sound — 150,000 probes found no inverted window and no
  NaN, and the `q.s` size jitter cancels exactly in `wext`.

**F5. The wading push is not scaled by `WIND.amp`.** *(Plains; design question.)*
Walking through forged grass parts it (`lean += ±prox * 1.4`), and that term is
added after `windLean` has already returned 0, so grass still moves with **Wind
motion: Off** and under **Reduce motion** — up to lean frame 2 at your feet.
Honest caveat: `main`'s own v8 proximity grass ignores Reduce motion in exactly
the same way, so this is parity, not a regression. But "is parting grass with
your legs *wind* motion?" is the same shape of question as 1a's "is the tide
wind motion?", and it is yours, not mine.

**F6. Ground with no blades under base pieces and along the spawn trail.**
*(Plains; looks deliberate, but you should confirm.)* `pbBuildTufts` skips the
spawn→forge trail ("the trail stays a trail", and README asks Plains for "worn
dirt tracks"), and `pbDrawTufts` skips the 3x3 ring under every base piece —
while `render` suppresses the old v8 tufts for the whole biome. So those tiles
keep the forged ground texture but carry no blades, where `main` had a few. For
the trail that is plainly the intent; for base pieces it is probably the intent
too (grass should not poke through a wall), but nothing says so.

**F7. `pbTuftSprite` has no fallback on a bake-budget miss.** *(Plains; would
change the look.)* `pbDrawTree` and `pbDrawDecor` both retry with the already-
baked `k = 0` frame when their lean frame is not cached yet; the tuft path does
`if (!e) continue;` and the blade simply vanishes for that frame. With 4 bakes a
frame, a gust that rolls a whole screen to a new lean frame can drop a few tufts
for a frame or two. Not seen in any of the 110 captured frames (489 tufts in
every one), so it is a first-seconds effect, but the inconsistency is real.

**F8. Props baked into a ground chunk during a forge backoff are lost until that
chunk is re-baked.** *(Plains; needs a design decision.)* One transient canvas
failure sets `pbBackoffUntil = now + 2000`, and for those two seconds `pbSprite`
returns `null` for everything *including* force bakes. Chunks baked in that
window are burned without props and are never re-baked while visible, so a
screenful of Plains permanently loses its stones and logs until the chunk falls
out of the 48-entry LRU. Tufts and trees recover on the next frame because they
are drawn live; baked props do not. The fix is a choice — exempt force bakes
from the backoff (which defeats the backoff's purpose on iOS) or re-bake chunks
when the forge recovers — so it is yours.

**F9. `pbAirChunks`, `pbAirCells` and `pbLifePlans` survive a world change.**
*(Not Plains — coast, forest and dark forest only.)* `groundCacheReset` reaches
`pbOnGroundReset`, which clears `pbTuftLists` and nothing else. `pbAirChunks`
caches terrain-derived lists (shore edge masks, dapple tiles, shaft tiles,
glow-mushroom sites) keyed by chunk with no seed, and is cleared nowhere in the
file — only LRU-trimmed at 140. After an admin world reset, with `coast` or
`forest` or `darkforest` on, up to 140 chunks keep drawing the *old* coastline
and the old forest floor, and the glow mushrooms also feed `collectLights`, so
night lights hang where nothing stands. Plains contributes nothing to any of
these three caches, which is the only reason this is out of scope.

**F10. The Dark Forest mist drifts with Wind motion Off.** *(Not Plains.)*
`spd = still ? 0 : 0.05 + 0.09 * WIND.s * WIND.amp` — the 0.05 base is not
scaled by `amp` and is applied along `WIND.dx/dy`, so at Off each mist bank still
slides 4.80 tiles downwind per 96 s cycle, and Low (0.0669) is not half of Full
(0.0839). The same shape applies to the forest dapples and shafts, which pulse
from `WIND.tS` inside an `if (!still)` that tests `reduceMotion` only.

**F11. Bee and dragonfly wing frames read the animation-frame timestamp.**
*(Not Plains.)* Position is world-clock driven, but the wing frame comes from
`pbLife_T`, the rAF stamp, so two clients at the same instant show different
wings. Cosmetic; it is the module header's "two clients agree on every animal"
claim that is wrong, not the picture.

**F12. The dormant layer is not quite free.** *(Not Plains-specific; unmeasured
here.)* With every switch false, `pbDrawTufts` still runs `pbCollectBaseTiles()`
every frame and can build up to 3 empty tuft lists a frame (256 `biomeAt` calls
each), and `pbLifeEnsure` still walks the visible cells. Both settle into cached
empties, but they re-pay on every new 48 s window and every camera move into new
cells. It also leaves one extra counted canvas operation a frame in run4's
proxy, from `pbDrawTufts` touching `imageSmoothingEnabled` before it knows it
has nothing to draw. An early `if (no switch is on) return;` would make the
dormant case actually dormant; I did not add one because it changes what the
existing op-counting gates measure and I had no second run4 to check it with.
